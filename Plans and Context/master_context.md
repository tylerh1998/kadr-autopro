# AutoPro Master System Context

*Living reference document, attached to future AI agents' context to explain how AutoPRO actually works at a system level — before they dive into specific code. **This variant of AutoPRO went live in production 2026-08-15** (`autopro.kensauto.ca`, `main` branch, Supabase project `hbcrwkmgsazqrvsrmxyr` - based on an older legacy base44 hosted application launched Jan 1, 2026 and developed from Oct 2025 and onwards.) — see §5 for cutover status and what's still open post-cutover. For the Base44 migration's full history and phase-by-phase execution detail, see `Archive/master_blueprint.md` and `Archive/blueprint_verification_plan.md` (historical reference only). For any still-open pre/post-go-live item, see `Pre_go-live_plan.md`/`go_live_checklist.md`.*

## 1) Purpose Statement
The all-in-one management solution for automotive repair shops, streamlining work orders, inventory, scheduling, payroll, and financials for efficient business operations.

## 2) Module Context & Architecture
*   **Sales & Work Management:** Work orders, estimates, invoices, notes, and WorkPRO integrations. Includes reporting on work order, sales, customer retention/loyalty, and tech efficiency. 
*   **Scheduling:** Appointments, Work Order/WorkPRO-calendar integrations, email and text reminders.
*   **Inventory Management:** Inventory item CRUD, returns, history, parts invoice entry, cores, levies, sales classes, categories, and inventory sales/history reporting.
*   **Customer Management:** Customer CRUD, history, Accounts Receivable (AR), system-wide email logging.
*   **Vehicle Management:** Vehicle CRUD and service history.
*   **Accounts Payable:** Supplier CRUD, Invoice transactions (charges/credits/payments), Lines of Credit (charges, credits, payments).
*   **Banking:** Cash drawer, bank accounts, transactions, reconciliations, transfers, cash flow tracking.
*   **Accounting:** Chart of accounts, balance sheet, P&L, financial dashboard, GL ledger, GST/taxes, journal entries, fiscal periods.
*   **Payroll:** Payroll transactions and ledger entries. **Future Feature: Full Payroll system - includes merger with PayPRO** (a sister application used to manage Employee Payroll/HR records, Pull reporting from WorkPRO tables, Calculate Payroll Amounts, Generate/Distribute Paystubs, Mark Paystubs as Paid, Calculate/Generate Payroll Remittances, Mark Remittances as Paid, Generate T4s and CRA XML Files, and Aggregate/Employee Payroll Reporting)
*   **Setup:** Global system settings and configurations — small config/lookup managers (`SystemSettings`, `WorkOrderStatus`, `TagAlong`, `OtherChargeList`) mostly consumed by other modules' editors (WO status dropdown, tag-along tire-tax UI, other-charge line items) rather than having standalone business logic of their own. Includes the Lankar legacy-data import tooling (admin-only, one-time-use) and the (deferred-indefinitely, no real test data available) legacy work-order upload/extract flow (`LegacyWorkOrderImportModal.jsx` + `autopro-processLegacyWorkOrder`).

**WorkPRO (Sister Application):** WorkPRO is a *separate application* from AutoPRO, not an AutoPRO module — it's the technician-facing side of the business: project tracking, pairing a Project to a Work Order, and time tracking (clock-in/out, tech time logs). It shares the same Supabase project as AutoPRO. AutoPRO reads/writes WorkPRO's tables (`Project`, `ProjectTimeSession`, `TimeRecord`, `UnassignedTime`, `Employee`, etc.) for features like tech time display and WO↔Project pairing. The integration flow is linear and deliberate: `Appointment -> WorkOrder -> Project`. Do not conflate the three concepts.

**Customer Portal (Sister Application):** The customer-facing counterpart to AutoPRO — a fully separate repo/app (`kadr-customer-portal`, its own Vite/React frontend, deployed independently to Vercel), not an AutoPRO page or module. It has no login: a customer views a work order or account statement via a public link carrying a `cp_id` capability token (~60-bit random alphanumeric — knowing the URL *is* the credential, same model as a DocuSign envelope link). It shares this same Supabase project. **AutoPRO is the minting side of the relationship:** this repo's own edge functions — `autopro-createPortalSnapshot` (invoked from `SESEmailModal.jsx`, `BatchSendWorkOrdersModal.jsx`, `InvoiceConversion.jsx`), `autopro-createStatement` (invoked from `StatementModal.jsx`), and `autopro-sendStatementEmail` — write the snapshot rows (`CustomerPortalWorkOrder`, `CustomerPortalStatement`) that the portal app later serves. They keep the `autopro-` prefix (not `custportal-`) because they run as AutoPRO functions in this repo, even though their entire purpose is feeding the other app. All of the portal's own verification/rate-limiting/lockout logic lives entirely on its side (`custportal-*` functions) — none of it exists here. **Confirmed cross-repo gap, AutoPRO-side root cause (2026-08-09, verified against the live `get_outstanding_ar_items` definition):** the portal's "drill from a statement into one specific historical work order" feature needs each statement transaction to carry a `work_order_id`, but `get_outstanding_ar_items` — the RPC `StatementModal.jsx` uses to build `CustomerPortalStatement.transactions` — returns only `id, type, reference, date, amount, ar_paid, balance, description, age_days`. No statement AutoPRO mints today can support that portal feature until this RPC (or the client-side shaping in `StatementModal.jsx`) adds the field. **⚠️ Shared-table RLS is currently wide open** on `CustomerPortalWorkOrder`/`CustomerPortalStatement`/`Approvals` (`policy: true` for role `public`) — anyone holding the portal's anon key (it ships in its client bundle, so effectively anyone) can read/write these tables directly via PostgREST, bypassing every one of the portal's Edge Function security gates. Deliberately left open because AutoPRO's own staff app may need direct read/write on these same tables — locking it down requires coordinating from the AutoPRO side too, not a change to make unilaterally from the portal repo alone.

## 3) Global Technical Rules & Conventions

*   **Supabase Edge Functions:**
    * Must always use the `autopro-[functionname]` naming format.
    * **Error Handling:** Edge Functions must return a `200 OK` status with an `{ error: "message" }` JSON payload instead of throwing raw 4xx/5xx HTTP errors. The Supabase JS client (`FunctionsHttpError`) intercepts non-2xx codes and swallows the JSON response body, hiding the actual error message from the frontend. (PDF-generating functions are a deliberate exception on their success path — they return raw PDF bytes with `Content-Type: application/pdf`; only their failure path uses the `{error}` convention.)
    * **Payloads:** Deno edge functions typically require payloads to be wrapped as `{ body: { ... } }` when invoking from the frontend via the Supabase client.
    * Constructing a third-party SDK client (e.g. Twilio) at module top-level is dangerous — a bad credential throws at construction time and crashes the *entire function*, including its CORS `OPTIONS` preflight handler. Build credential-dependent clients inside the request handler, after the `OPTIONS` short-circuit.
* **Base44 (legacy platform, deprecation now substantively complete — Phase 15, 2026-08-13):** AutoPRO used to round-trip a large share of its backend through a legacy Base44 SaaS platform (SDK, hosted functions, entity CRUD, auth) via a bridging `base44-proxy` Edge Function. That entire migration — 15 phases, full history archived at `Plans and Context/Archive/master_blueprint.md` and `Archive/blueprint_verification_plan.md` — is done: `@base44/sdk`/`@base44/vite-plugin` removed from `package.json`/`vite.config.js`, the SDK wrapper files (`base44Client.js`/`entities.js`/`integrations.js`) deleted, the local `base44/functions/` mirror tree hard-deleted, `base44-proxy` deleted from dev.  
*   **Entity & Table Verification:**
    * **RLS enabled with zero policies silently blocks all access**, with no clear error. Any "restored"/"copied" table needs its `pg_policies` row count checked. The standing convention across this project is one permissive policy: `CREATE POLICY "Enable all operations for all users" ... FOR ALL TO public USING (true) WITH CHECK (true)`.
*   **ID Generation:** Legacy-origin tables almost universally have `text` primary keys with **no working Postgres default** (a few, like `GLTransaction.id`, have a decoy default like `''::text` that looks real but produces useless empty-string collisions). Every native insert must generate its own id, client- or function-side. Two formats coexist across the schema — **check the specific table's live rows before choosing, never assume project-wide uniformity**:
    * 24-char lowercase hex (Base44/Mongo-ObjectId-style): `crypto.randomUUID().replace(/-/g,'').substring(0,24)` — used by `WorkOrder`, `Customer`, `Vehicle`, `InventoryCategory`/`InventoryLocation`/`ReturnReason`, `CashDrawerAdjustment`/`DepositSlipBreakdown`, and most other legacy-origin tables.
    * Standard 36-char UUID: `crypto.randomUUID()` unmodified — used by `InventoryItem` and `InventoryReturn`.
    * **Forgetting the client-generated id on a table with no DB default throws Postgres `23502` (NOT NULL violation), not a graceful error** — confirmed root cause of a real bug where `NewWorkPROModal.jsx`'s "Create New Project" path never set `Project.id`. Check this first for any "creating X silently fails" report on a legacy-origin table.
*   **WO/RO/EST/INV numbering is driven by a stored counter** (`SystemSettings.next_ro_number`, `next_inv_number`), not `max(existing_number) + 1` — it has no self-correcting safety net. After any bulk WorkOrder data copy/import (e.g. a production→dev refresh), this counter can silently drift behind real data, and the resulting collision doesn't surface at insert time — it surfaces later as a confusing `500` from `autopro-saveworkorderdata` ("multiple (or no) rows returned") because a `.single()`-style lookup by `ro_number` now matches 2 rows. Any process that bulk-copies/imports WorkOrder data must resync this counter afterward.
*   **Data Types — recurring traps:**
    * **`jsonb` columns come back already-parsed** from `supabase-js` — never `JSON.parse()`/`JSON.stringify()` them. Confirmed genuine `jsonb` columns: `WorkOrder.line_items`/`payments`/`accounting_details`/`tech_time`, `CashFlowSummary.pad_registries_details`/`overhead_items`, `CustomerPortalStatement.transactions`/`aged_balances`, `SupplierPayment.invoice_number`, `CashDrawerAdjustment.gl_transactions`. The defensive read-side pattern used throughout the codebase where legacy code still might send a string: `typeof x === 'string' ? JSON.parse(x) : x`.
    * **A jsonb array column can hold a double-encoded JSON *string* instead of a real array — confirmed to have actually happened, not just a theoretical risk.** Root cause: a frontend save path did `JSON.stringify(lineItemsToSave)` before writing `WorkOrder.line_items` to its jsonb column (fixed in `buildWorkOrderSavePayload.js` — pass the real array, let `supabase-js` serialize it; `autopro-saveworkorderdata` also unwraps a string payload defensively before writing, as a second layer). At worst (2026-08-13) this had corrupted **67% of `WorkOrder` rows on dev (1,088 of 1,613) and 1,166 rows on production** — **fully backfilled and resolved 2026-08-14** (`Pre_go-live_plan.md` P12, full detail/results in `p12_line_items_backfill_plan.md`): every corrupted row converted via a proven-lossless `(line_items #>> '{}')::jsonb` cast, verified with byte-identical financial aggregates and zero spurious audit-history entries (see that plan for the `audit_workorder_changes`-trigger-suppression technique used, worth reusing for any future bulk technical fix on this table). **Zero corrupted rows remain on either project as of this writing.** The lesson stays evergreen regardless: any **raw SQL** touching a jsonb column (not just JS reads) must guard against a scalar sneaking in — `jsonb_array_elements()`/`jsonb_array_length()` throw outright on one. Standing defensive pattern, still in place (harmless now that the underlying data is clean, but a real safety net against any future regression), used by `get_parts_movement_v2` and `search_work_order_parts`: `CASE WHEN jsonb_typeof(col)='string' AND TRIM(col #>> '{}') LIKE '[%' THEN (col #>> '{}')::jsonb WHEN jsonb_typeof(col)='array' THEN col ELSE '[]'::jsonb END`.
    * **The inverse trap also exists** — some columns that *look* like they should be structured are genuinely still `text`, and the existing `JSON.parse()`/`JSON.stringify()` calls around them are correct and must be preserved (e.g. `PayrollTransaction.additional_deductions`). Always check the live Postgres column type before assuming either direction.
    * **Stringy booleans:** `Customer.is_active`, `Vehicle.is_active` (and similar) are `text`, holding `'true'`/`'false'`/`'0'`/`'f'`/`'n'`/`'no'`/`null` — use `.or('is_active.eq.true,is_active.is.null')`, never a plain `.eq('is_active', true)`.
    * **`ChartOfAccount.account_number` is `bigint`, but every GL-account-carrying column across the schema that stores a *selected* account number is `text`** (`BankAccount.gl_account`, `BankTransaction.gl_account`, `CustomerARAdjustment.gl_account`, form state defaults like `'4013'`, etc. — `LinesOfCredit.gl_account`/`OtherChargeList.gl_account` are the exception, also `bigint`). A raw shadcn `<Select>`/`<SelectItem value={account.account_number}>` populating from `ChartOfAccount` passes a number where the bound value is a string; Radix's strict-equality match against the current value silently fails — the dropdown's option list still renders fine (no match needed there), but the trigger shows blank instead of the selected account. Confirmed and fixed across 6 files 2026-08-13 (`CashDrawerAdjustmentModal`, `BankTransactionModal`, `BankAccountEditModal`, `RecordAdjustmentModal`, `LinesOfCreditEditModal`, `ReceiveCreditModal`, `OtherChargeForm`) by casting both the `Select`'s bound `value` and every `SelectItem`'s `value` to `String(...)`. The codebase's own `GLAccountCombobox` component (`src/components/suppliers/GLAccountCombobox.jsx`) already did this correctly (`String(account.account_number) === String(currentValue)`) — match that pattern for any new GL-account picker rather than a raw `Select`.
    * **`bigint` columns silently reject fractional values** (Postgres `22P02`) with no visible error if the caller's `{error}` check is missing/incomplete — the UI can show a value optimistically that never actually persists. Any dollar-amount column should be `double precision`, not `bigint`, proactively. Recurring instances: `CashFlowSummary` (12 fields), `Levies.total_amount`/`base_amount`, various denomination columns, `Employee.pay_rate` (fixed 2026-08-14, was throwing `22P02` on any decimal pay rate entered via `TechDirectory.jsx` — see `Pre_go-live_plan.md` P3 for the full audit trail). PostgREST serializes `numeric`/`decimal` as a genuine JSON number, not a string — no frontend regression risk from widening `bigint` → `numeric(10,2)`, confirmed via a raw REST call.
    * **Two remaining bigint columns are latent instances of this same bug class, audited 2026-08-14, not yet fixed because neither is currently reachable:** `SystemSettings.shop_supply_rate` (stores a whole-number percentage like `6`, correctly `/100`'d everywhere it's read — but has no editable UI anywhere in `src/` today, so nobody can yet trigger a fractional-percent write) and `PayPeriods.total_pto_hours`/`total_stat_hours` (hours could plausibly be fractional, but `PayPeriods` is referenced nowhere in `src/` or `supabase/functions/` — a dormant/orphaned table). If either ever gains a real write path (a Setup UI for shop supply rate, a payroll import writing to `PayPeriods`), widen to `numeric`/`double precision` proactively rather than waiting for the same bug to resurface.
    * **Text-typed number fields** need an explicit cast before arithmetic and an explicit `String()`/stringify before write: `LinesOfCreditTransaction.balance`, `PayrollTransaction.amount`. Always strictly cast (`Number()`/`parseFloat()`) — JS string-concat bugs (`"5"+"1"="51"`) have caused real data corruption historically.
    * **Text-typed date/timestamp columns:** several date fields are plain `YYYY-MM-DD` text, not real `date`/`timestamp` columns (`CustomerPayments.payment_date`, `CustomerARAdjustment.adjustment_date`, `InventoryReturn.return_date`/`date_returned`, `GSTReturn.period_start_date`/`period_end_date`). Any SQL needing these must cast directly to `::DATE` — casting through a timezone (`::TIMESTAMPTZ AT TIME ZONE ...`) assumes UTC midnight and shifts the displayed date back a day.
*   **"Schema replayed to production" ≠ "data replayed" ≠ "feature works there."** Four distinct failure modes recur, all confirmed multiple times independently:
    1. **Zero rows copied.** A reference/config table (`SystemSettings`, `CashFlowSummary`, `OtherChargeList`) can exist correctly on production with the right RLS while still holding zero rows. Verify row counts match between branches after any schema replay, not just table presence.
    2. **RLS enabled, zero policies — on Storage buckets too, not just tables.** Same landmine as the table-level one above, but also hit `storage.objects` (the `kadr-digital_invoice_uploads` bucket existed on production but not dev, and once created had zero of its two required policies). Check `pg_policies` with `schemaname='storage'` in addition to the target table's own schema.
    3. **Table+RLS correctly replayed, but the Edge Function that writes to it was never deployed to the target project** (`autopro-createStatement` missing from production despite `CustomerPortalStatement`'s schema being replayed weeks earlier). Fast check: `get_edge_function` returning `NotFoundException` on the target project. Do this proactively for every function writing to a newly-replayed table, don't wait for a silent-`catch` bug report.
    4. **A column an Edge Function's code already depends on was never added to schema on *either* branch via a tracked migration at all** — not replay drift, a genuine gap. `SentEmailLog.appointment_id` was written into `_shared/resend.ts`/`_shared/twilio.ts`/both reminder functions' insert calls from the start, with no migration ever creating it on dev *or* prod (dev had it patched in out-of-band at some point; prod didn't, until caught and fixed manually 2026-08-13 — see §4.2). Nastier than modes 1–3: the insert fails, but since `logAndSendEmail`/`logAndSendSms` insert the log row *before* sending, the failure silently kills the actual send too, not just the audit trail. Fast check: query `information_schema.columns` directly rather than trusting a function's own insert payload as proof a column exists.
    5. **A function/RPC exists correctly on dev — even extensively live-tested there — but was never migrated to production at all, and stays invisible because production's old app never called it.** The sharpest confirmed instance of this whole pattern, found the day of the go-live cutover itself (2026-08-15, see §5): `set_workorder_lock`, `search_work_orders`, `search_work_order_parts`, and `autopro_search_entities` all existed correctly on dev (some already documented elsewhere in this doc as if mature/tested — they were, on dev) but had **no equivalent on production at all**, not a missing migration file, missing from the database outright. Harmless for as long as production ran the old Base44-hybrid app that never called any of them; the instant the DNS cutover made production's native frontend live, all four broke at once — `set_workorder_lock`'s failure was silently swallowed (see §3's locking note and §4.1), the other three surfaced as outright `PGRST202`/"function not found" errors on core pages (WorkOrders list, Open RO search, Find Part in Work Orders, admin OmniSearch). Caught and fixed same-day (migration files written, `apply_migration` run against `hbcrwkmgsazqrvsrmxyr`, confirmed live via direct `pg_proc` query). **Standing lesson: a feature working on dev proves nothing about whether it will work the first time production's own frontend actually exercises it.** Any cutover-style event — a new environment going live, a branch flip, a dormant feature getting its first real caller — needs an explicit RPC/function inventory diff between the two projects, not just a table/schema diff.
*   **Two live Supabase projects exist and do not always match**: `hbcrwkmgsazqrvsrmxyr` = `main`/production, `sitihbdnuxifwibontcm` = `development` (what `test.kensauto.ca` actually runs against). A schema/data/deploy check against one never implies the same state on the other — confirmed divergences have included missing columns (`CustomerPortalWorkOrder.cvip`/`odometer` existed on dev, missing on production until backfilled) and entire tables/RLS/functions being dev-only. Always state which project a finding applies to; re-verify independently before assuming production matches.
*   **Each Supabase branch/project has a fully independent Auth service** — separate JWT signing keys, separate `auth.users`. A production-issued session JWT is rejected by dev's PostgREST and vice versa. This is the root cause of a whole class of "mysterious 401" symptoms when testing against the wrong branch with the wrong session. The `/dev-login` route (`src/lib/DevLogin.jsx`) issues real, branch-native Supabase Auth sessions for testing native `supabase.from()`/`.rpc()` call sites directly with proper RLS — useful for verifying a fix's live database behavior independent of full frontend rendering (decode the resulting `supabase-auth-token` cookie, then call REST/RPC/Edge-Function endpoints directly via `fetch` with that JWT).
*   **Postgres triggers + audit RPCs:** direct `.update()` calls can conflict with triggers expecting session context. Where a dedicated audit RPC exists (e.g. `update_inventory_with_audit`, which sets `set_config` session variables the `trg_inventory_audit` trigger reads before writing to `InventoryAuditLog`), it is **mandatory** for that class of write — a raw `.update()` bypasses the audit trail entirely and/or produces duplicate/corrupted log rows if mixed with a manual log insert. **`update_inventory_with_audit` has two live overloads** (a 10-param legacy form and an 11-param form adding `p_source_record_id`) — same class of PostgREST overload-ambiguity risk as `search_inventory_ranked` once had (see §4.1/§4.3); always call the 11-param form so callers resolve consistently.
*   **Realtime/WebSocket subscription effects must not depend on churn-prone state.** A `useEffect` that opens a Supabase Realtime channel should subscribe once (`[]` deps) and read current state/handlers via a `ref` updated every render — not list page/sort/search/tab state in its dependency array. Doing so tears down and rebuilds the socket on every unrelated interaction (typing in a debounced search box, changing pages), and the async subscribe/unsubscribe can race, permanently breaking live updates after the first churn while looking connected. Confirmed as the root cause of a "WorkOrders live-refresh only works on page load" bug, fixed 2026-08-11 in `WorkOrders.jsx`.
*   **Fiscal Period gate:** any function that moves real money must call the shared `checkFiscalPeriodStatus()` pattern (`src/components/utils/fiscalPeriodUtils.jsx`) before writing, gated on the transaction's date — reject if the covering `FiscalPeriod` is closed or doesn't exist. This is the single most important cross-cutting rule in the Accounting domain; confirmed callers span nearly every money-moving surface in the app (AP, LOC, Inventory receiving, Bank transfers, Levies, Deposits, WO payments). New GL-posting functions should copy this guard from an existing one rather than omit it.
*   **`Promise.all` poisoning:** batching a still-legacy (`base44.*`) call with an already-native call in one `Promise.all` means a single legacy 401 blanks the *entire* result set, including the native calls that would have succeeded. This recurred repeatedly across many files during migration. Always isolate native fetches from legacy fetches with independent error handling (e.g. separate `.catch()`s) rather than assuming a mixed batch is safe.
*   **Unbounded fetch + PostgREST row cap:** PostgREST enforces its own default row cap (`db-max-rows`, raised on this project from the default 1000 to 10,000 as of 2026-08-08) independent of any SQL-level `LIMIT` — a `LIMIT NULL` (unbounded-by-design) RPC call is still truncated at the API layer. Combined with a sort order that isn't scoped to the caller's intended subset (e.g. `search_work_orders`'s default `number_desc` sorts by invoice-only columns, `NULLS LAST` for every other stage), an "fetch everything, filter client-side" query can silently starve out the very rows it's looking for once one stage's row count approaches the cap — invoice-stage rows crowded out `WorkOrder`'s Estimates/WIP tabs down to single digits this way. Always pass an explicit scope filter (e.g. `p_stages`) rather than relying on cap headroom for correctness; raising the cap is not a fix, only a delay.
*   **Supabase Edge Functions are not deployed by a frontend push:** pushing to `origin/development` only updates the Vercel-hosted frontend — `supabase/functions/*` source sitting in the repo is inert until separately deployed (Supabase MCP `deploy_edge_function`, or `supabase functions deploy`). A function edit that appears to have zero live effect is more likely an un-deployed function than a code bug — confirm via `get_edge_function`'s `updated_at`/version before assuming otherwise.
*   **Two GL-posting functions are permanently protected — never modify:** `autopro-handleInvoiceConversionGL` and `autopro-handleSupplierInvoiceLineGL`. Every other module (Banking, AP, LOC, GST, Levies, Payroll) is free to post its own GL entries directly/independently — this is an intentional, coexisting pattern, not something to consolidate into the two protected functions.
*   **Optimistic locking — three tiers, and the one that looks "mature" is currently the riskiest lock in the app:**
    * **`BankAccount`/`LinesOfCredit`:** the genuinely mature two-column (`locked_by_user`/`locked_timestamp`) pattern — atomic CAS acquire, a stale-lock timeout allowing a second CAS-based steal, and a dedicated flush/admin-unlock action. No known open issues.
    * **`WorkOrder` (via `set_workorder_lock` RPC) — do not copy this as "the" mature pattern; it has real, currently-open holes.** A remediation plan exists (`Plans and Context/implementation_plan_wo_locking.md`, **pending approval as of this writing, no code changes made yet**) documenting three confirmed live gaps: (1) the RPC silently auto-steals the lock from its current holder after 120 minutes with zero warning to either user; (2) **nothing anywhere checks lock ownership before writing** — not the general Work Order save, not any of the three inventory-affecting actions that bypass save entirely (Get Part, Receive Parts, Mark Parts as Ordered) — so a stolen or contested lock is a silent last-write-wins collision, and for the inventory actions specifically, a real risk of physically pulling stock from QOH while the record of it ever landing on the Work Order gets dropped; (3) tab-close lock release is currently **dead code**, for two independent, Base44-era reasons — it gates on a token (`src/lib/app-params.js`) the current native-auth flow never populates, and even if it didn't, it posts to the wrong URL entirely. **`set_workorder_lock` itself didn't even exist on production until 2026-08-15**, created the same day as the go-live cutover after its total absence — silently swallowed into `console.error` while the UI showed the lock as "acquired" regardless — was caught (§3's schema-replay note, failure mode 5; §5). **Dev and production currently run two genuinely different definitions of this same function, not just different data:** dev's is the older, more elaborate version described above (with the flawed auto-steal); production's (today's emergency same-day fix) is a deliberately minimal `apply`/`release`-only version with no staleness/steal logic and no admin-override action at all — check which project you're looking at before trusting either one as "the" current behavior. `WorkOrders.jsx`'s "Flush Locks" button (`handleFlushLocks`) remains live, real, and completely unguarded — one click clears every Work Order lock in the system, no admin gate, no per-record scoping. The pending remediation plan would remove the auto-steal, add ownership checks at every write path (with an explicit "someone else holds this — override?" confirm for real user actions, a silent fail for autosave), fix tab-close release, and replace system-wide "Flush Locks" with a scoped per-Work-Order "Clear Lock" action — none of that has shipped yet.
    * **`Supplier`:** a single bare `LockedByUser` text column — no timestamp, no staleness detection, no flush mechanism. A crashed tab can permanently lock a supplier with no automatic recovery today. This is a real, permanent gap, not something a later phase silently fixed — know it before debugging a "why can't I edit this supplier" report.
*   **Identity / audit fields:** `created_date`/`created_by`/`created_by_id` are the standard insert-audit trio; most legacy-origin tables have **no** `updated_by`/`updated_by_id` (only `updated_date`) — don't assume symmetry. `WorkOrder` is a further exception, using `last_updated`/`last_updated_by` instead of the `updated_date` convention used elsewhere.
*   **UI/UX Standards:**
    * Use accessible, soft UI patterns (Tailwind CSS, Radix primitives via `shadcn/ui`).
    * Implement robust error boundaries, loading skeletons, and graceful degradation — especially for data sourced from a not-yet-fully-migrated entity, which should hide/stub gracefully rather than error.
    * **Right-click `ContextMenu` (Radix) is the row-action pattern app-wide, not left-click** — `ChartOfAccounts.jsx`, `LineItemsTable.jsx` (WO parts grid: "Get Part"/"Cores"/mark-ordered/etc.), `InventoryReturns.jsx` (Edit Return Info, Receive Credit). A `cursor-pointer` row with no obvious left-click affordance is a strong signal to try right-click before concluding an action doesn't exist.
    * **The app's light-mode `--background` CSS variable (`src/index.css`) is currently a medium gray-blue (`hsl(215 20% 65%)`), not white** — git history shows it was originally `hsl(0 0% 100%)` and changed as a likely-accidental side effect of an unrelated commit (`5112f687`, "Layout changes and Login", 2026-07-24); every other neutral token in the palette (card/secondary/muted/sidebar) is 96–100% lightness by contrast. Confirmed as the root cause of at least one real contrast bug (a `text-red-600` warning message reading as "hardly visible"). **Deliberately kept as-is per user decision (2026-08-13)** — not a bug to silently "fix" by reverting; any new colored text/border placed directly on the page background (not inside a `bg-card`/white surface) should be checked for contrast against this actual gray tone, not assumed-white.
    * **A derived/computed flag threaded through multiple independently-written state-copying code paths is fragile by construction** — `InventoryAdd.jsx`'s `is_existing` "New" badge was only set in one of three paths that could produce/copy the same object, silently wrong in the other two with no error. Prefer recomputing a derived flag fresh at its actual point of consumption over carrying it as state through every path that touches the object it lives on.
*   **Never trust a checked-in `.sql` file as proof of an RPC's real live signature/params** — the repo's own `search_customers_ranked.sql`/`search_inventory_ranked.sql` sources have both been stale against what's actually deployed (a claimed param that never existed on any live version; a dropped duplicate overload not reflected in the file). Verify via `pg_get_functiondef(oid)` against the live database before relying on a function's documented signature. A `DROP FUNCTION` targeting the full explicit parameter list (not just the name) safely removes one specific overload without risk of dropping the wrong one.
*   **Use `fetch(..., { keepalive: true })` whenever code must reliably notify the backend right before a hard navigation** (`window.location.href`, `beforeunload`/`pagehide`) — a normal awaited fetch has no delivery guarantee once the page starts unloading. Root cause of a real, hard-to-hit Supplier-lock-stuck-forever bug: a cheque-payment success path did a hard redirect bypassing React Router (and every one of the page's normal lock-release paths), and the `beforeunload` fallback routinely lost the race against unload. Same pattern used by `DocumentEditor.jsx`'s WO-save keepalive mechanism (see §3's Base44 note on `app-params.js` — that one's confirmed broken, with a remediation plan pending).
*   **A same-named component file can exist in two different folders with entirely unrelated responsibilities** — e.g. `src/components/bank/DepositDetailsModal.jsx` (presentational only) vs. `src/components/cash-drawer/DepositDetailsModal.jsx` (real `BankAccount`/`reverseDeposit` logic). Always grep the full path, never assume a same-named file elsewhere is a duplicate or the "same" component.
*   **Every live Postgres function/RPC change made via the Supabase MCP tools (`apply_migration`) needs a matching `.sql` file written into `supabase/migrations/`** — the MCP tool changes the live database immediately but leaves zero trace in the repo. A function created/fixed only through `apply_migration` is invisible to `git diff`/code review and would be lost on a clean migration replay, even though the live app behaves correctly in the meantime. Confirmed as a real gap (not hypothetical) during the Supplier Statement Reconciliation build (§4.5) — `get_supplier_reconcile_invoices` existed correctly on the dev database for multiple turns with no corresponding repo file until caught and backfilled.
*   **Filtering/exclusion rules on data that gets grouped into a conceptual/aggregate record (e.g. `SupplierInvoiceLine` rows grouped by `invoice_number`+`invoice_date` into a conceptual invoice) must be evaluated on the aggregated result, not per source row.** A per-line `WHERE` filter applied before grouping can silently drop a legitimately-paid line from an otherwise-still-open multi-line invoice (understating the subtotal shown), or fail to exclude a multi-line invoice that only nets to zero/blank in aggregate. Confirmed as a real bug in `get_supplier_reconcile_invoices`'s first version — fixed by moving both the "not fully paid" and "not blank" checks to run against `SUM()`'d invoice-level totals after the `GROUP BY`, never against individual line rows before it.
*   **Live verification protocol — three hard rules:**
    1. **Hold verification until commit + push + deploy are done.** A change only becomes testable once it's committed, pushed to `origin/development`, and — if any `supabase/functions/*` file was touched — separately deployed via the Supabase MCP `deploy_edge_function` (a frontend push does **not** deploy Edge Functions; see §6). Don't tell the user to "go check" or attempt any live-browser verification against uncommitted/undeployed work — there is nothing for them to see yet.
    2. **Live-test only at `test.kensauto.ca`.** This is the Vercel-hosted `development`-branch frontend, wired to the dev Supabase branch (`sitihbdnuxifwibontcm`) — the one environment where a pushed change actually becomes visible/testable.
    * **`localhost` is never a viable substitute, for two independent reasons:** it fails on a TLS/certificate error, and separately the authentication system requires same-origin and won't work against a local dev server even if the cert issue were bypassed. There is no local-dev-server testing path in this project — full stop. Full push/deploy mechanics and known agent-side limitations (e.g. `git push` not working from an agent CLI session) are in §6.
    3. **Production (`autopro.kensauto.ca`, `main`, `hbcrwkmgsazqrvsrmxyr`) is genuinely live as of 2026-08-15 (§5) — real shop traffic, real customer data being written, not a dormant mirror.** Never use it as a place to "just check" a fix — verify on `test.kensauto.ca`/dev first, always. A production deploy is a deliberate, coordinated action taken with the user's explicit go-ahead (frontend and backend together when contract-coupled, per the Bulk Receive Parts precedent in §4.1), never a routine same-session action.
*   **The dev Supabase branch holds real, production-copied customer data** (confirmed via the production data copy performed ahead of live verification — every table except `GLTransaction` reflects real customers, real emails, real phone numbers). Any new automated or scheduled feature capable of independently triggering a customer-facing email/SMS — i.e. not gated behind a human clicking "send" in the UI — **must default to a test-mode allowlist** (compare the resolved recipient against an env-var-configured allowlist, skip/log everything else, flip to live only via an explicit secret change) before it's ever scheduled to run unattended on dev. Not optional per-feature judgment — this is the precedent the native Appointment Reminders (below) were deliberately built around, after a prior session avoided running the original functions unscoped against dev for exactly this reason.
*   **Scheduled/unattended Edge Function triggers use `pg_cron` + `pg_net`** — a distinct mechanism from the table-trigger pattern (`WorkOrder_Broadcast`, `sync_customer_to_google`). A `cron.schedule(...)` job (tracked in a migration file) calls `net.http_post` against the function's URL on a fixed schedule. Since `pg_net` carries no user session, the called function can't use normal JWT auth (`verify_jwt: false` is required) — auth instead comes from a custom header (e.g. `x-cron-secret`) checked against a secret. **Never inline that secret's raw value in migration SQL** (`cron.job` is readable via schema access, the same exposure class as the hardcoded-JWT anti-pattern already fixed on `WorkOrder_Broadcast`/flagged on `sync_customer_to_google`) — store it in `supabase_vault` and reference `vault.decrypted_secrets` from inside the cron job body instead. First instance of this pattern: the two Appointment Reminder cron jobs (§4.2) — dev branch only as of 2026-08-10, **now live on both branches as of 2026-08-13** (prod promotion: functions deployed, prod's own `autopro_cron_secret` Vault entry created — Vault is per-project, not shared across branches — and `AUTOPRO_CRON_SECRET` function secret set). **Confirmed trap when promoting a `cron.schedule(...)` migration from dev to prod: the migration file's `net.http_post` URL is a project-specific literal, not something that resolves per-environment.** The reminder migration's checked-in `.sql` still had dev's host (`sitihbdnuxifwibontcm`) hardcoded from when it was authored/tested there — applying it unmodified to prod would have pointed prod's own cron at dev's functions. Always rewrite the host to the target project (verify via `get_project_url`) before applying a migration file across branches — never trust the checked-in literal. **`20260815000000_remove_workorder_broadcast_hardcoded_jwt.sql` has this exact same unresolved landmine** (dev's URL hardcoded in its trigger body), not yet fixed since it was outside this session's scope — confirm/correct its host before ever applying it to prod. Production's `WorkOrder_Broadcast` trigger is already confirmed live and correctly pointed at its own URL today (via whatever's actually deployed under applied-migration name `20260812173808`, which does not match this checked-in file's content) — so this is a repo/live drift risk to fix before the file is ever (re-)applied, not a currently-broken feature.
*   **`supabase/functions/_shared/` is the project's first shared Edge Function code** (`resend.ts`/`twilio.ts`) — centralizes the "send via Resend/Twilio + log to `SentEmailLog`" logic that used to be copy-pasted per function. Any *new* email/SMS-sending function should import from here rather than adding another copy. The pre-existing functions that already worked (`autopro-sendEmailViaSMTP`/`-sendStatementEmail`/`-sendARReceiptEmail`/`-sendBatchWorkOrderEmails`/`-sendSms`, both `report-issue` functions) were retrofitted onto the low-level `sendViaResend`/`sendViaTwilio` helpers only, deliberately **not** the higher-level `logAndSendEmail`/`logAndSendSms` wrapper — that wrapper hardcodes single-recipient, and some of those functions genuinely need the comma-separated multi-recipient support the wrapper doesn't provide. `SentEmailLog.tracking_id` (Resend message id / Twilio SID), written on send, is later matched by the inbound side: `autopro-resendWebhook` (a native port of the original base44-hosted webhook) updates `SentEmailLog.status` on Resend's delivery callbacks (`sent`/`delivered`/`bounced`/`complained`/`delivery_delayed`/`opened`/`clicked`) — no signature verification, a faithful port of the original's own lack of one, not an oversight to silently add. **Deployed to both branches as of 2026-08-13** (was dev-only; prod was missing the function entirely — `get_edge_function` returned `NotFoundException`, another instance of §3's schema-replayed-but-function-not-deployed pattern, mode 3). Resend's dashboard webhook config still needs to be manually repointed at each branch's own URL (`https://hbcrwkmgsazqrvsrmxyr.supabase.co/functions/v1/autopro-resendWebhook` prod, `https://sitihbdnuxifwibontcm.supabase.co/functions/v1/autopro-resendWebhook` dev) — Resend's own dashboard, no available tooling for it; as of this writing it may still point at the base44-hosted version instead.
*   **Dark mode is a first-class, fully-supported theme app-wide** — class-based via a `dark` class on `document.documentElement`, toggled in `Layout.jsx`, preference persisted on `Employee.dark_mode`. Tailwind `dark:` classes are strictly additive (`bg-white dark:bg-slate-900`, never a bare replacement). This convention applies to any new UI built from this point forward, not just retrofits — full palette and lesson history live in `Antigravity-context-plans/master_blueprint.md` §7.
*   **`cn()`/`tailwind-merge` silently drops a conflicting utility rather than erroring — this can make an entire `DialogContent` invisible with zero console error.** `tailwind-merge` treats `fixed`/`relative`/`absolute`/`static`/`sticky` as one conflict group and keeps only the *last* one in the merged class list. shadcn's base `DialogContent` is `fixed` (required for its `top-[50%] left-[50%] translate-x-[-50%] translate-y-[-50%]` viewport-centering to work) — passing a custom `className` that also includes `relative` (often added out of habit to give an absolutely-positioned child a positioning context, usually unnecessary since `fixed`/`absolute` on the parent already establishes one) silently strips `fixed` from the final output. The dialog still renders — `data-state="open"`, fully populated, `display`/`visibility`/`opacity` all normal — just positioned in normal document flow at whatever the centering-transform math produces relative to that flow instead of the viewport, typically hundreds of pixels off-screen below the fold. Symptom: user sees the dark overlay backdrop but nothing else, no error anywhere. **Confirmed root cause of `SchedulerViaWoModal.jsx`'s invisible scheduler modal (fixed 2026-08-13).** The same investigation also caught an adjacent, unrelated-cause bug in the same component: its custom close button was hidden too, because it was a *direct child* of `DialogContent`, which carries `[&>button]:hidden` (meant only to suppress Radix's own default close button — itself also a direct child) — fixed by wrapping the custom button in a plain positioning `<div>` so it's no longer a direct-child match for that selector. Check both patterns — an unwanted `relative` in a custom `DialogContent` className, and any custom button placed as a direct `DialogContent` child when `[&>button]:hidden` is present — on any other report of a Dialog rendering blank or missing its close control.
*   **Print output has two safe patterns and one dangerous one.** Safe: (A) a fully separate `window.open()` document, entirely outside the app's React tree/`.dark` class; or (B) a reused on-screen DOM with an explicit `@media print` color-reset that forces all `dark:`/CSS-variable-token colors to fixed light values. Dangerous: a reused on-screen DOM using only `visibility`/`display` toggling with no color-reset — if the user is in dark mode when they print, the output silently inherits dark colors. Any new print/paper-preview feature must use pattern A or B.

## 4) Module Functionality and Operations

*Per-module business logic, data model, and cross-module integration — the "how it actually works" layer. Full migration-project execution/testing history is archived at `Plans and Context/Archive/master_blueprint.md`/`Archive/blueprint_verification_plan.md` (historical lookup only — see §5); current outstanding items live in `Pre_go-live_plan.md`/`go_live_checklist.md`.*

### 4.1 Sales & Work Management (Work Orders Core)

**Data model.** `WorkOrder` is the central entity — 24-char-hex `id`; `ro_number` is the stable identifier across the whole lifecycle, with `wo_number`/`est_number`/`inv_number`/`crinv_number` auto-derived from its digits per stage. **`stage`** (not `status`) is what actually drives page-redirect/UI logic: `estimate` → `work_order` → `invoice` → `credit_invoice`, or `void`. `line_items`, `payments`, `accounting_details`, `tech_time` are genuine `jsonb` (see §3). Each `line_items[]` entry's core-tracking fields: `Core_num` (capital C, quantity of core units), `core_ret` (quantity returned), `core_cost`, and **computed** `core_osamt = (Core_num - core_ret) * core_cost` — never store `core_osamt` as an editable input. Related tables: `Approvals` (portal approvals), `CustomerPortalWorkOrder` (portal snapshots, keyed by a unique 10-char `cp_id` — minted here, served to customers by the separate Customer Portal app, see §2), `SentEmailLog` (SMS/email audit, `pending`→`sent`/`failed` lifecycle), `InventoryReturn` (backs core/warranty returns), `Levies` (see §4.7), `SystemSettings`/`WorkOrderStatus`/`TagAlong`/`OtherChargeList` (small config/lookup tables consumed by the editor).

**Lifecycle.** Estimate→Work Order conversion performs a **QOH/QOO allocation split** per line item — a requested quantity can split across "available now" (QOH) vs "still on order" (QOO), each portion written via `update_inventory_with_audit`, called twice per split line (once tagged `'Issued to WO'`, once `'Ordered'`) so the audit trail keeps both as distinct rows. Each line's inventory step is error-isolated so one bad line doesn't fail the whole conversion. Work Order→Invoice conversion triggers GL posting via the protected `autopro-handleInvoiceConversionGL` function (§3) — a live-verified example produced 8 balanced GL rows including COGS/inventory-reduction entries and a penny-adjustment line when needed to zero the balance exactly. Only estimate-stage WOs can be voided. **(2026-08-07 addition)** the same conversion function also finalizes any line with `qty_quoted > 0` — see "Quoted parts" below — into a real on-order commitment, since a converted WO can't remain "just quoted."

**Locking.** `set_workorder_lock` RPC — see §3's Optimistic Locking note for the real, currently-open gaps (silent auto-steal, no ownership check anywhere before a write, dead tab-close release, dev and production running two different definitions of the function) and the pending remediation plan (`implementation_plan_wo_locking.md`, not yet approved/built). The `beforeunload`/`pagehide` keepalive-fetch path exists (`dispatchBackgroundSaveOrRelease` in `DocumentEditor.jsx`) but does **not** currently release the lock — broken for the Base44-era reasons detailed in §3, not a working parallel path today.

**Live refresh (Zero Polling, confirmed live end-to-end 2026-08-06).** `WorkOrder` has an `AFTER INSERT OR UPDATE OR DELETE` trigger (`WorkOrder_Broadcast`, a single multi-event trigger — **not** three same-named single-event triggers, which silently overwrite each other since trigger names are unique per table) that fires the `WorkOrder-Broadcast` edge function via `pg_net`/`supabase_functions.http_request` (async, non-blocking — cannot fail or delay the underlying `WorkOrder` write), broadcasting `{table, event_type, source_id, timestamp}` on Supabase Realtime channel `work_order_refresh`, event `workorder-updated`. The frontend (`WorkOrders.jsx`) subscribes via a **separate client** (`src/lib/supabaseRealtimeClient.js`), not the app's normal authenticated `supabase` client, and calls `loadData()` on receipt. See §3's realtime-subscription-effect gotcha before touching this subscription. Any future table wanting the same live-refresh behavior should follow this exact trigger→edge-function→broadcast shape rather than inventing a new one.

**Security hygiene fix, both dev and prod, 2026-08-11/12:** the trigger previously carried a hardcoded `Authorization: Bearer <JWT>` header. Investigated and confirmed the JWT was each project's own public anon key (not a service-role key or third-party credential) and, more importantly, that `WorkOrder-Broadcast`'s own code never reads the incoming `Authorization` header at all — it authenticates internally via the auto-injected `SUPABASE_SERVICE_ROLE_KEY`. Fix was to drop the header entirely (not relocate it to Vault) and set the function's `verify_jwt: false` on dev to match prod's existing setting. Separately, `supabaseRealtimeClient.js` itself hardcoded **production's** URL/anon key regardless of which environment the rest of the app was configured for — meaning dev's live-refresh could never have worked at all, independent of the trigger's own credential. Fixed on `development` (2026-08-11) to read `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` like the regular client. **Confirmed carried over at the 2026-08-15 go-live cutover** — `main` now equals `development`'s content, so it inherited the env-var fix automatically; no separate action was needed. Full history: `Plans and Context/Archive/workorder_broadcast_update_plan.md`.

**Quoted parts (2026-08-07).** Two mutually-exclusive-in-practice sibling fields live on each `line_items[]` entry: `qty_on_order` (a real commitment — `InventoryItem.quantity_on_order` was actually bumped) and `qty_quoted` (a customer-facing price quote with no inventory commitment yet — the linked `InventoryItem` exists, at 0 QOH/QOO if newly created, but its QOO was deliberately left untouched). `WOAddInventoryModal.jsx`'s batch-add offers both **Add Batch as On Order** (legacy path — bumps QOO and writes an `InventoryAuditLog` row, `tx_type: 'Ordered'`) and **Add Batch as Quoted** (creates/links the `InventoryItem` the same way but skips both). On the Estimate stage, On Order is hidden entirely (`mode === 'estimate'`) — estimates can only quote, never place a real order. A still-open quoted line has two separate promote/consume paths, both reachable from `LineItemsTable.jsx`'s context menu: **Mark Parts as Ordered** (`MarkPartsOrderedModal.jsx` + `autopro-processWorkOrderMarkQuotedOrdered`, gated on `mode !== 'estimate'`) finalizes the quote into a real QOO commitment — identical mechanics to the conversion path above. **Receive Parts** (`ReceivePartModal.jsx` + `autopro-processWorkOrderPartReceive`) is the path for when the part is already physically in stock — pulls straight from QOH; on-order-sourced lines also unwind `quantity_on_order`, quoted-sourced lines don't (there was never a commitment there to unwind). **As of 2026-08-15 this is a single bulk flow, not two separate single-line ones** — see the dedicated paragraph below; the formerly-separate `ReceiveQuotedPartModal.jsx`/`autopro-processWorkOrderReceiveQuotedPart` pair this paragraph used to describe was deleted and folded in. The "Quoted (Not Ordered)" badge — long-flagged as deferred work in the Phase 2 archive plan — now reads `qty_quoted` (rose-colored) instead of the old `not_ordered` boolean; `not_ordered` stays in the schema/payload untouched for old records but no longer drives any UI. **Gotcha, confirmed as a real live bug:** batch-added line items get a raw JS-number `id` (`Date.now() + Math.random()`), not a string — comparing it against an id that's been round-tripped through a plain JS object's keys (`Object.keys()`) silently fails, since object keys are always coerced to strings while `Set.has()`/`===` stay type-strict. Hit this exact bug in both `autopro-processWorkOrderMarkQuotedOrdered` and its frontend local-state sync (`WorkOrderForm.jsx`); fixed by `String()`-normalizing both sides before comparing. Check for this same bug class anywhere else that threads a `line_items[].id` through an object-keyed structure.

**Parts import via paste/upload OCR (2026-08-07).** `WOAddInventoryModal.jsx`'s Add Part flow also has a **Paste/Upload Parts** button (`WOPartsImportModal.jsx`) that bulk-populates the batch table from a cart/order-confirmation screenshot or PDF, reusing the shared `autopro-processPartsInvoiceOCR` function (§4.3) via an additive `documentContext: 'wo_parts'` prompt branch — same JSON schema, existing receiving-flow behavior unchanged when the param is omitted. A supplier is chosen once up front for the whole import session rather than per-item (no fuzzy-matching needed, unlike `InventoryAdd.jsx`'s receiving flow). This introduced the codebase's first clipboard-**paste** image-capture UI (`onPaste` reading `e.clipboardData.items`), feeding the same file queue as the existing upload input. Full history: `Plans and Context/Archive/woaddparts_Import_Plan.md`.

**Receive Parts — rewritten as a bulk flow (2026-08-15).** `ReceivePartModal.jsx` (same file/component name, contract rewritten in place) and `autopro-processWorkOrderPartReceive` (same function/endpoint, same in-place-rewrite treatment) now handle every receivable line on a Work Order in one table — Part Info+checkbox / Qty On Order-Quoted / Qty On Hand / Apply to WO — instead of one line at a time, gated table-wide (`mode !== 'estimate'` and at least one line has `qty_on_order > 0` or `qty_quoted > 0`) rather than per-row, mirroring how "Mark Parts as Ordered" is already gated. `ReceiveQuotedPartModal.jsx`/`autopro-processWorkOrderReceiveQuotedPart` are fully superseded and deleted from the repo — **the old function slug is still deployed on production as of this writing**, harmless dead code now that nothing calls it, a cleanup candidate rather than a bug. The rewritten function derives each line's source (on-order vs. quoted) server-side the same way the old context menu did (`qty_on_order > 0` takes precedence over `qty_quoted`), keeps a running per-`inventory_item_id` QOH/QOO map seeded from live values so multiple selected lines sharing one inventory item can't double-spend the same stock within a batch (same technique as `autopro-processWorkOrderMarkQuotedOrdered`'s `runningQOO` map), and reports any line it couldn't fully satisfy in a `skipped[]` array rather than failing the whole batch — and actually surfaces it in the UI, closing a gap `MarkPartsOrderedModal.jsx` still has today (its backend already returns `skipped[]`, its UI still doesn't show it). The payload contract changed (`{ receipts: [{lineItemId, quantity}] }` instead of one line at a time) — frontend and backend were deployed to production back-to-back the same day specifically because of that coupling; confirmed both sides live and in sync (production's `ReceivePartModal.jsx` sends the new shape, `autopro-processWorkOrderPartReceive` v19 expects it).

**WorkOrders list/search (`search_work_orders` RPC).** Backs `WorkOrders.jsx`'s main list and `OpenROModal.jsx`'s Open RO search — stage filter, free-text search across RO/WO/EST/INV/PO numbers and customer/vehicle fields, 6 sort modes, server-side pagination via a `total_count` field on each returned row. Like the other RPCs in §3's schema-replay note (failure mode 5), this one existed correctly on dev but had no production equivalent at all until the 2026-08-15 cutover surfaced the gap — now live on both.

**Core returns (FIFO).** Filters `InventoryReturn` by `part_number`+`work_order_id`+`status:'On-site'`, sorts FIFO by `return_date` then `created_date` as **plain string comparisons, not date-typed** (must be preserved exactly), pre-checks total available quantity before mutating anything, then consumes fully-consumed records via delete and partially-consumed records via update.

**Warranty returns.** Only reachable when `stage === 'invoice'`. Stamps the line item's `warranty_returned` integer flag (`1` = returned) inside `line_items[]`, writes the array back, and inserts its own GL reversal rows (a separate direct-insert path from §"Lifecycle" above).

**Levies sync.** `Levies` now exists as a real native table with 3 functions (`autopro-syncLevies`, `getReportableLeviesReport`, `postLeviesToAP` — see §4.7 for the algorithm). The WO-save trigger call site (`useDocumentEditorSave.jsx`) intended to fire `syncLevies` on every save — **verify its current wiring status directly (grep the call site) before assuming it's connected; as of `Archive/blueprint_verification_plan.md`'s final state this was still flagged as an open gap, not a resolved integration, and was never re-confirmed after.**

**Documents & communications.** PDF generation (`generateWorkOrderPdf`, jsPDF-based) and portal-snapshot generation both apply the same business rule — **payment totals exclude `on_account` payments** — treat this as one shared rule, not two independent implementations, if it's ever changed. SMS/Email both log a `pending` `SentEmailLog` row *before* the send, then update to `sent`/`failed` after; email failure triggers an internal shop-notification email as a deliberate side effect. `SentEmailLog.tracking_id` and the inbound Resend delivery-callback update path are covered in §3's `_shared/`/`autopro-resendWebhook` note. Notes Board gives unplaced notes a deterministic round-robin fallback placement (`% 3` across a per-column running counter) — preserve the exact algorithm so unplaced notes land in a stable spot.

**Integration.** → **Inventory**: all quantity mutations go through `update_inventory_with_audit`; part-to-add search via `search_inventory_ranked` (8-param signature, `search_inventory_ranked(text,text,text,text,integer,integer,text,text)` — always pass `p_location_from`/`p_location_to` explicitly, even as `null`, to avoid PostgREST overload ambiguity). **`search_work_order_parts` is a separate, simpler 3-param RPC** (`p_search_term, p_search_type, p_filter_type`, no location params — don't conflate the two) backing the standalone **"Find Part in Work Orders"** feature (`FindPartModal.jsx`, reachable from the top nav) — searches every WorkOrder's `line_items[]` for a part/serial number across the whole system, not part of the line-item-adding flow. Its `FROM "WorkOrder" wo, jsonb_array_elements(wo.line_items) li` join throws outright on any row where `line_items` isn't a true jsonb array — must wrap with the defensive `CASE`/`jsonb_typeof` pattern in §3's jsonb-scalar-corruption note; fixed 2026-08-13 (was previously crashing the whole search once it hit any of the corrupted rows). → **GL**: delegated to the two protected functions (§3), plus direct-insert paths for warranty reversals. → **Customer/AR**: `customer_id`/`vehicle_id` FK fields; re-parenting a WO to a different customer also bulk-updates linked `CustomerPayments.customer_id` — this two-statement operation is **explicitly non-atomic**, matching legacy behavior. → **WorkPRO**: `Project.work_order` matches `WorkOrder.wo_number` by plain text, no FK — see §4.9.

**Estimate→WorkOrder→Invoice conversion is a multi-phase wizard, not a single click** — odometer capture → internal description → payment settlement, in that order (Counter Sales skip the odometer/description steps). Confirmed correct even in the edge case of an advance payment taken while still at Estimate stage: the advance-payment liability GL account (`2100`) clears to $0 as part of final invoice settlement rather than double-booking or going stale.

### 4.2 Scheduling / Appointments

### 4.3 Inventory Management

**Data model.** `InventoryItem` (36-char-UUID id): `part_number`, `description`, `cost`, `selling_price`, `quantity_on_hand`/`quantity_on_order`, `supplier_id`. **`location`/`category` are plain name-string text columns, not FKs** into the lookup tables below — those tables exist to drive dropdown lists/validation, not relational integrity. `InventoryCategory` (`name`), `InventoryLocation` (`location_name`, `is_active`), `ReturnReason` (**field is `reason`, not `name`** — a real naming trap) all use 24-char-hex ids. `InventoryReturn` (36-char-UUID id, 32 live rows historically): `return_type` (app-enforced discriminator text — `"core"`/`"return"`/`"warranty"`, not a DB constraint), `status` (`"On-site"`/`"Returned"`), `return_date`/`date_returned` (text, `yyyy-MM-dd`). `InventoryAuditLog` is the real, authoritative movement-history table, populated by the `trg_inventory_audit` trigger as a side effect of `update_inventory_with_audit` writes.

**Receiving.** `InventoryAdd.jsx` (optionally OCR-assisted via `autopro-processPartsInvoiceOCR`, a pure Gemini-vision prefill with zero DB writes) saves through `autopro-processInventoryReceipt`: handles create/edit/reverse of `SupplierInvoiceLine` records, updates QOH/QOO exclusively via `update_inventory_with_audit`, checks `FiscalPeriod.is_closed`, rounds all money math to the cent (including a largest-remainder GST-proration algorithm across multiple lines), and **delegates GL posting** to the separate `autopro-handleSupplierInvoiceLineGL` function rather than posting inline — receiving/inventory logic never posts GL directly, a deliberate architectural boundary. The same `autopro-processPartsInvoiceOCR` function is shared by WO Add Part's Paste/Upload Parts import (§4.1) via an additive `documentContext: 'wo_parts'` prompt branch — a second consumer, not a fork.

**QOH adjustment → GL.** `autopro-processQOHAdjustment` posts `value_change = quantity_change * item_cost`, rounded to the cent both for the nonzero-change decision *and* the GL amount (float artifacts like `9.990000000000002` must not produce fractional-penny rows or false nonzero checks): increase → debit `1200` (inventory asset)/credit `5003` (adjustment expense); decrease → the reverse.

**Audit pattern.** Any write changing `quantity_on_hand`/`quantity_on_order` **must** go through `update_inventory_with_audit` — the one confirmed exception is non-quantity field changes (e.g. `LocationModal.jsx` reassigning `location`, a plain `.update()`).

**Category AI-suggestion.** `autopro-suggestInventoryCategory`: hardcoded shortcut if `supplier_name` contains `"jard"` (case-insensitive) → `"Jard"`, no AI call. Otherwise a single Gemini `gemini-flash-latest` call grounded with `google_search` tool (temperature 0.1, **no JSON response mode** — grounding and structured-output mode aren't reliably combinable on this model), classifying into an existing `InventoryCategory` name; falls back to `"other"` on no match.

**Returns — one table, workflows differentiated by `return_type`.** `InventoryPartsReturnModal` (pre-bills COGS, `"return"`/`"core"`), `EditReturnInfoModal` (edits any type, no GL), `WarrantyReturnModal` (post-bills COGS from an already-invoiced WO, `"warranty"`), `LegacyWarrantyReturnModal` (LANKAR items never received into this system — **creates a brand-new `InventoryItem` on the fly** at 0 QOH/QOO before creating the return, since no receiving record exists; a genuinely different pattern from the other three).

**Tire / tag-along missing-warning convention.** Any part-entry surface that lets a user manually key in a part (as opposed to OCR-imported) must independently run the same tire-detection check the OCR path runs — it does not fall out for free just because both paths feed the same batch/review list. Detection: keyword match (`/\btire(s)?\b/i` against part number/description/category) or a tire-size regex (`P225/60R16`-style patterns); if a part matches and has no Tag Along selected, it's flagged (`missing_tire_tax`) and shown with a red warning badge plus a save/process-time confirm dialog the user can override. Confirmed duplicated (deliberately, not extracted to a shared helper) across `InventoryAdd.jsx` (both its OCR `handleOCRSuccess` path and, as of 2026-08-08, its manual `handleAddToBatch` path) and `WOAddInventoryModal.jsx` (WO Add Part, both its OCR import and manual-entry paths, added 2026-08-08) — a future fifth part-entry surface needs the same logic ported in explicitly, not assumed inherited.

**Note:** `search_inventory_ranked` silently excludes `is_active: false` items from every in-app part search — by design (an item deactivated e.g. via merge becomes invisible to search), not a search bug. `InventoryCategory` and `ReturnReason` have **no dedicated admin CRUD screen** — both are only populated via inline "Add" affordances inside consuming modals (category suggestion in `InventoryAddModal.jsx`, return-reason dropdown in `InventoryPartsReturnModal.jsx`). `InventoryLocation` does have a real admin path (`LocationModal.jsx`'s "Add Location" tab, via `InventoryList.jsx`'s row context menu → "Edit Location").

**Integration.** → **Suppliers/AP**: receiving creates `SupplierInvoiceLine`s; GL delegated to `autopro-handleSupplierInvoiceLineGL`. → **Work Orders**: `search_inventory_ranked`/`search_work_order_parts` RPCs for part search; core-tracking fields live in `WorkOrder.line_items`, conceptually shared with `InventoryReturn.return_type = "core"` but owned/migrated on the WO side. → **GL**: three distinct entry points (QOH adjustment, receiving's delegated function, and direct-insert warranty-return postings) — prefer delegating to a dedicated GL function over inline posting wherever one already exists for the workflow.

### 4.4 Customer & Vehicle Management (incl. Accounts Receivable)

**Data model.** `Customer`/`Vehicle`: `is_active` is stringy-boolean text (§3); no DB-side id/timestamp defaults. `CustomerPayments`: `amount`, `ar_pmt`/`ar_paid` (double), `ar_applyto` (text), `deposited` (bool), `gl_posted`, `work_order_id`. `CustomerARAdjustment`: `amount`, `ar_paid`, `overpayment` (bool) — **no `ar_applyto` column**, adjustments aren't a payment "source" in the same sense (except via the `credit_source` mechanism below, tracked on the payment side). **`ar_paid` sign convention** (both tables): `balance = amount - ar_paid`. A charge (`amount > 0`) is paid down by *increasing* `ar_paid` toward `amount`. A credit (`amount < 0`, e.g. an overpayment) starts with a negative balance (available credit); consuming `$X` makes `ar_paid` *more negative* (`newArPaid = ar_paid - amountApplied`). **`ar_applyto` format** (`CustomerPayments` only): comma-separated `id:type:amount:description` entries; `type` ∈ `'pmt'` (applied to a charge), `'adj'` (applied to a positive adjustment), `'credit_source'` (the credit that funded this payment) — a free-form string field, so new types need no schema change. **GL accounts**: `1100` = AR control, `1010` = Cash, `2100` = customer-deposit/overpayment liability (system-generated overpayment adjustments only — a manual credit can carry any `gl_account`, always read the row's own value, never hardcode).

**Merges.** Customer merge (`autopro-mergeCustomers`): fill-if-empty on a fixed field list, duplicate's notes appended under a `--- Merged Data ---` separator, cascades `customer_id` across `Vehicle`/`WorkOrder`/`CustomerPayments`/`CustomerARAdjustment`, deactivates (never deletes) the duplicate with an audit note. Vehicle merge (`autopro-mergeVehicles`): same fill-if-empty pattern plus "keep highest mileage" and "keep newest odometer date" special cases; cascades `vehicle_id` on `WorkOrder`.

**AR payment application (credit-aware `create_payment`, in `autopro-processCustomerARAccounting`).** `buildOutstandingCharges` returns both positive-balance charges and negative-balance credits, oldest-first. Charges to pay are either user-selected or an oldest-first walk up to the payment amount; eligible credits are either explicitly selected or (in "oldest" mode) all folded in automatically. Credit is applied oldest-charge-first; `netCashNeeded = totalChargesSelected - creditAppliedTotal`. If cash is still needed, a normal `CustomerPayments` row posts with standard `1010`/`1100` GL legs. If credit fully covers the selection, a `CustomerPayments` row still gets created (`payment_method: 'credit_applied'`) so the existing reversal machinery works, but with **no `1010` cash leg** — only credit-consumption GL entries (debit the credit's own `gl_account`, credit `1100`). `ar_applyto` records both the charge/adjustment entries and one `'credit_source'` entry per credit drawn on.

**Reversal (`reverse_payment`).** Blocked if `payment.deposited === true`. Rolls back `ar_paid` on genuinely-external charge/adjustment entries; fully reverses-and-deletes payment-*generated* adjustments (credit-card fee, overpayment); restores credit-source `ar_paid` (ceiling at 0). Posts an offsetting GL entry and deletes the payment row — reversal is always via a balanced offsetting entry, never GL deletion.

**Adjustment-reversal guard (`reverse_adjustment`).** Closes an integrity gap: an adjustment with `ar_paid !== 0` (already paid down or already consumed as a credit source) is rejected from deletion — deleting it would orphan whatever payment/credit is applied against it and permanently corrupt the balance. Applies to all adjustments, positive or negative.

**AR interest (`autopro-calculateARInterest`).** Read-only. 30-day grace period per charge, then compounds monthly at 24% APR / 2%/month: `(1.02)^monthsOverdue`. Only returns customers with `totalInterest > 0.01`. "Apply Interest" bulk-inserts one `CustomerARAdjustment` + GL rows per customer via the same `create_adjustment` machinery.

**Statement portal (`autopro-createStatement`).** Writes `CustomerPortalStatement` (`transactions`/`aged_balances` as genuine `jsonb`, matching the shape `get_outstanding_ar_items` already produces — see §2's Customer Portal note for a confirmed gap in that shape). `portal.kensauto.ca/statement?cp_id=...` is served by the separate `kadr-customer-portal` app (§2), reading this table natively via its own `custportal-getPortalStatement` function — **no longer the legacy backend**, now that that app has completed its own base44 removal. Same relationship for the WorkOrder customer portal reading `CustomerPortalWorkOrder` via `custportal-getPortalWorkOrder`.

**AR aging/drill-down.** `get_customer_ar_transaction_page(customer_id, start, end)` RPC returns `{transactions (jsonb), opening_balance, current_balance}` in one call, transactions pre-joined with their linked `WorkOrder`. `get_outstanding_ar_items(customer_id)` powers Take-Payment/Statement invoice selection (both charges and credits, no sign filter).

**Fixed 2026-08-14, both dev and production:** `search_customers_ranked` used to never match "First Last" full-name searches — its `WHERE` clause only checked `org_name`/`first_name`/`last_name`/`email`/`phone` individually, never the concatenated full name (the `ORDER BY match_rank` logic's full-name-match rank tiers were dead code as a result — the row got filtered out before ranking ever ran). Confirmed before the fix: searching `'Tyler Haney'` returned 0 rows, `'Haney'` alone returned matches. App-wide impact, 6 call sites: `Customers.jsx`, `NewWorkOrderModal.jsx`, `ChangeCustomerModal.jsx`, `MergeCustomerModal.jsx`, `VehicleForm.jsx`, source `src/supabase/search_customers_ranked.sql`. (`AppointmentForm.jsx`'s customer search uses a different mechanism, unaffected.) Fix: added a concatenated-full-name match to the `WHERE` clause; verified via direct SQL on both projects post-fix (a real production customer, "Candace Sikora," now correctly matches at rank 3; existing single-term searches unregressed). **No live UI click-through was ever performed** on either environment (no agent login access; user authorized the production promotion directly off the SQL evidence) — if either search box ever behaves unexpectedly, this is the first place to check. Full detail: `pregolive_p1_p3_p4_batch_plan.md`.

**Integration.** → **Work Orders**: on-account charges are `CustomerPayments` rows with `payment_method = 'on_account'` — exactly what `buildOutstandingCharges` treats as AR balance. → **Banking/Cash Drawer**: `deposited` boolean gates both reversal eligibility and cash-drawer visibility — `.or('deposited.eq.false,deposited.is.null')` for undeposited queries. Cash-drawer bucket visibility is governed purely by `payment_method` list membership (`CashDrawer.jsx`'s fixed `paymentMethods` array) — any method absent from that list (`on_account`, `credit_applied`) is automatically excluded from cash reconciliation with no extra filtering logic needed; this is the standing mechanism for keeping non-physical-money payment types out of the drawer. → **GL**: every AR mutation posts through the same shared function, so a change there has app-wide AR blast radius.

### 4.5 Accounts Payable — Suppliers & Lines of Credit

**Data model.** `Supplier`/`SupplierInvoiceLine`/`SupplierPayment` (24-char-hex ids). **`SupplierPayment.invoice_number` is a genuine `jsonb` array** — never `JSON.parse()` it (§3). `LinesOfCredit`/`LinesOfCreditTransaction`: `line_of_credit_id` has a real FK (`ON UPDATE CASCADE ON DELETE RESTRICT` — Postgres itself blocks deleting an LOC with existing transactions); `LinesOfCreditTransaction.balance` is `text`, must be parsed before arithmetic. `ChartOfAccount` is conceptually owned here but read for GL-account dropdowns across nearly every module.

**Payment flow.** Two-step, asynchronous by design: `processSupplierPayment` validates and inserts a `pending` `SupplierPayment`, then fires-and-forgets an invoke of `executeSupplierPayment`, which resolves accounts, builds the GL pair, and calls the atomic Postgres RPC **`process_payment_atomic(p_payment_id, p_gl_entries, p_bank_tx)`** — the canonical pattern in this codebase for "post GL rows + a bank transaction together, atomically." For cheque payments it also bumps `BankAccount.next_cheque_number`.

**Invoice-line save (`saveSupplierInvoiceTransactions`).** Four ordered phases: deletions (skipping lines with nonzero `paid_amount`), additions, modifications (field-diffed for GL relevance), then payment reallocation across the supplier's existing payments. GL edits use reversal-then-repost. Direct GL account numbers: `2000` = AP, `2003` = GST Paid, plus the line's own dynamic `gl_account`.

**`SupplierInvoiceLine.invoice_date` format corruption (2026-08-14).** A line can get saved with `invoice_date` as `MM/DD/YYYY` instead of the table's `YYYY-MM-DD` convention if a `Ctrl+S`/`Ctrl+$` keyboard-shortcut save fires before the date field's `onBlur` normalizes it (`SupplierTx.jsx`'s `handleLineChange` clears `dateError` on every keystroke, so the flag can't be trusted at save time) — and `SupplierPaymentModal.jsx`'s "Make Payment" table parses `invoice.invoice_date` with no guard (unlike `SupplierTx.jsx`'s own `safeFormatDate`), so a malformed date throws during render and white-screens the app (no error boundary exists anywhere in this codebase). Fixed 2026-08-14 with three layers: `handleSaveAll` now re-validates/normalizes every date via `parseAndValidateDateInput` before saving, `autopro-saveSupplierInvoiceTransactions` rejects non-ISO dates server-side, and a CHECK constraint (`invoice_date_iso_format`) backstops the column — added `NOT VALID` since one pre-existing bad row (STAPLES Business Depot, id `7c30415c330840f783c120fe`) violated it, then fully `VALIDATE CONSTRAINT`'d once that row was corrected manually the same day. **Still open:** `SupplierPaymentModal.jsx`'s "Make Payment" table itself was never hardened against a malformed date (unlike `SupplierTx.jsx`'s own `safeFormatDate`) — a future bad row from any other write path would still white-screen the app on render (no error boundary exists anywhere in this codebase).

**Payment cancellation (`cancelSupplierPayment`).** Fiscal-gated → locates and validates (rejects if `cleared`/`reconciled`) the linked `BankTransaction`/`LinesOfCreditTransaction` → reverses `paid_amount` across affected invoice lines → posts a GL reversal → deletes the payment row → triggers `calculateBankBalances` if bank-sourced.

**Lines of Credit.** `processLineOfCreditTransaction` handles create/edit/delete of manual charges/credits in one function (edit = full reverse-then-reapply, both old and new dates fiscal-checked). `calculateLineOfCreditPaymentBreakdown` is read-only FIFO oldest-first matching (credits settle first each iteration, then charges). `processLineOfCreditPayment` resolves a target LOC and a payment source (another LOC or a `BankAccount`), applies charges additively, and posts GL + a source-side effect. `cancelLineOfCreditPayment` reverses a payment, cross-linking `is_reversed`/`reversed_by_id` on both sides. **Known, permanent asymmetry:** a cross-LOC payment cancellation restores the *target* LOC's balance but **not** the *source* LOC's — confirmed matching legacy behavior and preserved deliberately, not a bug to re-flag.

**`LinesOfCredit.current_balance`/`available_credit` are stored but non-authoritative — do not trust or "fix" them in isolation.** Neither `processLineOfCreditPayment` nor `cancelLineOfCreditPayment` updates these fields for the account being paid down (confirmed via grep + a source comment: "Removed backend recalculation logic as we no longer track balances here"). This looks like a major accounting bug until you check `LinesOfCredit.jsx`'s actual ledger page — it computes its displayed balance live from `LinesOfCreditTransaction` history and never reads these two columns. The real remaining exposure is narrow: `LineOfCreditPaymentModal.jsx`'s dialog header displays the stale field, and `LinesOfCreditEditModal.jsx` allows editing it directly. **General lesson:** before calling a "stored field is wrong" finding a bug, grep whether that field is actually load-bearing anywhere — it may be legacy/vestigial with the real source of truth computed live elsewhere.

**Supplier Statement Reconciliation** (`ReconcileSupplier.jsx`, `StatementUploadCard.jsx`, `ReconcileInvoiceGroup.jsx`, `ReconcileErrorGroup.jsx`, `lib/reconcileMatching.js`, `autopro-processSupplierStatementOCR`, `autopro-getSupplierReconcileInvoices`). Upload a supplier's PDF/image statement; a Gemini-vision edge function extracts each invoice/credit-memo row (explicitly excluding actual payments and balance-summary rows, per prompt instruction — same temperature-0.1 pattern as other OCR functions in §4.3) plus, as of 2026-08-08, two statement-level fields read directly off the document rather than computed: `period_start`/`period_end` (the statement's own covered date range — collapses to a single date when the statement prints one date rather than a range, not a bug) and `total_amount_due` (the statement's own printed total/balance-due figure). `matchStatementToAutoPro`/`findDiscrepancies` (`lib/reconcileMatching.js`) sort statement rows against AutoPro's conceptual invoices into four buckets: Not In AutoPro, Not On Statement, Matched, and Errors. **Errors is a 3-tier second pass over pass-1's total-amount-only leftovers, not a date/invoice-number check** — Tier 1: exact normalized invoice-number match with a differing total (`"Invoice Total Mismatch"`); Tier 2 (only tried if Tier 1 doesn't apply): a digit-transposition (same cents digits, different order) or decimal-shift (~10x/100x) relationship between the two amounts, regardless of invoice number; Tier 3 (weakest, last resort): plain close-dollar-amount fallback (`$2` or 2%, whichever is larger), labeled `"Close Amount Match — Verify"` since it carries real risk of pairing two unrelated invoices that coincidentally cost about the same. Invoice date is deliberately excluded as an Errors signal entirely — the separate `dateMismatch` badge on exact-total `Matched` pairs is the only date-related flag this feature has, and it's informational, not an error. **Triage convention (2026-08-08):** AutoPro invoices dated after the statement's extracted `period_end` are further split out of "Not On Statement" into a separate, lower-priority "After Statement Period" bucket (teal, non-selectable) rather than being lumped with real discrepancies or silently dropped — reconciling before every post-period entry exists is normal, not an error; the split only happens when `period_end` was actually extracted, otherwise "Not On Statement" is left unsplit. Only "Matched" is selectable and feeds "Add to Cash Flow"; the other three buckets are read-only. The printable report (`window.print()`-driven, gated by `@media print`) mirrors the same bucket split, with the letterhead logo and title in a two-column layout and the report timestamp including time-of-day (so two printed copies pulled the same day can be told apart). Reuses `SupplierPaymentModal.jsx`'s existing "Add to Cash Flow" pattern verbatim (`AddToSheetModal.jsx`, one `CashFlowEntry` insert) rather than reimplementing it — pushes the sum of checkbox-selected Matched invoices as a single **lump-sum** entry (no per-invoice traceability column exists on `CashFlowEntry`, the same limitation the reused flow already has), with Matched invoices auto-selected by default (opt-out, not opt-in). The page acquires no `Supplier` lock (§3's weaker single-column pattern) since its only write is that one `CashFlowEntry` insert — deliberate, not an oversight. Full history: `Plans and Context/Archive/reconcilesupplier_implementation_plan.md`.

**Integration.** → **Banking**: every AP/LOC money movement flows through `process_payment_atomic` or direct `BankTransaction`/`GLTransaction` inserts, always followed by `autopro-calculateBankBalances`. `ReceiveCreditModal.jsx` (physically an Inventory-return-flow file) routes refunds to one of 3 destinations — Supplier AP, Cash Drawer, or LOC — each with its own write path. → **GL**: independent direct posting throughout this module (§3) — never routed through the two protected functions.

### 4.6 Banking & Cash Drawer

**Data model.** `BankAccount` (two-column lock pattern, §3), `BankTransaction` (`debit_amount`/`credit_amount`, `source_type`/`source_id`; `is_reversed`/`reversed_by_id` columns exist but are **unused** by `reverseDeposit` — see below), `BankReconciliation` (`is_balanced` is derived, not stored), `CashDrawerAdjustment`, `DepositSlipBreakdown` (denomination columns are `bigint` — cast/default to `0`/`null`, never `''`).

**Deposit flow.** Cash Drawer item → "For Deposit" → Make Deposit → Deposit Slip Breakdown → one `BankTransaction` + 2 balanced `GLTransaction` rows + one `DepositSlipBreakdown` row, sharing a `deposit_batch_id`; marks the source `CashDrawerAdjustment.deposited = true`.

**`reverseDeposit` (7 ordered steps).** Validate the target transaction is an un-cleared, un-reconciled deposit → fiscal-period gate → find and flip-sign-reverse the original GL rows (tagged `source_type: 'deposit_reversal'`) → un-deposit the matching `CustomerPayments` rows → reset matching `CashDrawerAdjustment` rows → **hard-delete** the `BankTransaction` (deliberately not a soft reversal via the unused `is_reversed` columns — permanent, intentional legacy behavior) → recompute balances via `calculateBankBalances`. Never touches `DepositSlipBreakdown`.

**`calculateBankBalances`.** Sums `credit_amount - debit_amount` across non-reversed transactions, writes `BankAccount.current_balance`/`last_recalculated_date`. **The universal "recompute after any bank-affecting write" primitive** — reused by AP, LOC, Payroll, GST, and Bank Transfer.

**Reconciliation.** `processBankReconciliation` is a read-only CSV-vs-system amount matcher (±0.005 tolerance, amount-only). `batchReconcileTransactions` updates `reconciled`/`cleared`/`reconciliation_id` for a batch, returning HTTP `207` for partial success — a deliberately preserved non-`200+{error}` signal, an exception to the usual convention.

**Bank Transfer (`autopro-transferFunds`).** Validates both accounts are active with a `gl_account`, inserts 2 cross-referencing `BankTransaction` rows + 2 balanced GL rows, recalculates both accounts' balances. The fiscal-period guard was **deliberately added** during the native port (legacy never had it) — matches the project-wide convention, not a bug fix to undo.

**Integration.** Every other money-moving module (AP, LOC, GST, Levies, Payroll) posts through `BankAccount`/`BankTransaction` and always calls `autopro-calculateBankBalances` afterward — this module supplies the shared money-movement primitives for the whole system, even though the actual write sites for e.g. supplier payments live in the AP module's own files.

### 4.7 Accounting — GL Reporting, Taxes, Fiscal Periods, Levies

**`FiscalPeriod`** is the central gating table for the whole system — see §3's `checkFiscalPeriodStatus()` rule.

**GL Reporting suite.** Mostly read-only aggregation over `GLTransaction`/`ChartOfAccount` (a couple, like `getGeneralLedgerData`, are thin RPC passthroughs). Balance Sheet construction validates `isBalanced` (Assets = Liabilities + Equity) directly in its output. `findGLImbalances` can trigger an email alert via `autopro-sendEmailViaSMTP` when imbalances are found. `postJournalEntries` validates debits = credits before writing any row, with rollback-on-partial-failure.

**GST.** `calculateGSTReturn` (read-only) sums `GLTransaction` rows filtered by account number against `SystemSettings`'s configured collected/paid accounts; `total_sales`/`total_purchases` are computed via **string range comparisons** on `text` account numbers (`>= '4000' && < '5000'` for sales, `>='5000' && <'7000'` for purchases) — deliberately string-based, not a bug. `postGSTJournalEntries` builds up to 4 GL rows with **sign-aware debit/credit branching** that flips depending on whether the balance is positive or negative — this branching must be preserved exactly. `processGSTPayment` requires the `GSTReturn` be `status==='posted'`, posts a sign-aware GL pair + `BankTransaction`, and calls `calculateBankBalances` (a deliberate addition beyond the legacy source, for consistency).

**Levies pipeline** (a fully separate, append-only ledger design — do not reimplement as an overwrite):
- **`syncLevies`** (fired on WO save, must stay cheap/non-blocking — errors are swallowed and only logged, never blocking the WO save itself): reads `OtherChargeList` rows flagged `reportable_levy`, walks WO line items, computes each reportable line's target state, diffs against existing `Levies` rows for that WO, and inserts **delta rows** representing the net change (never overwrites/replaces existing rows) — removed lines get a zero-balancing negative delta.
- **`getReportableLeviesReport`** — read-only, resolves `work_order_id` to a real RO/WO/EST/INV number with a multi-field fallback scan, joins `OtherChargeList` descriptions.
- **`postLeviesToAP`** — fiscal-gated. Groups in-range `Levies` by `other_charge_id`, validates each charge type has a `linked_supplier_id`, computes a quarterly invoice number/date, inserts one `SupplierInvoiceLine` per group (`gl_account: '5001'`, `gst_override: true`) plus a balanced GL pair (debit `5001`/credit `2000`), then marks the source `Levies` rows as remitted by pointing them at the new invoice line. The fiscal guard here was likewise deliberately added during the native port.

**Cash Flow.** `CashFlowSummary` (single-row config) auto-creates a fresh row if none exists — a self-healing fallback, not an error state. `CashFlowEntry` is a drag-reorderable sheet with debounced `sort_order` persistence (owned data-model-wise by the AP module, edited on this domain's `CashFlow.jsx` page).

**GL account number reference** (a shared vocabulary referenced — sometimes hardcoded — across many modules' posting code):

| Account | Meaning |
|---|---|
| `1010` | Cash |
| `1100` | Accounts Receivable |
| `1200` | Inventory asset |
| `2000` | Accounts Payable |
| `2001` | GST Payable/Receivable |
| `2002` | GST Received/Collected |
| `2003` | GST Paid |
| `2052` | CPP payable |
| `2053` | EI payable |

**Integration.** `FiscalPeriod` reachability has historically been the single biggest recurring live-testing blocker across Banking/AP/LOC — any "write silently reverts" symptom should first rule out a still-legacy-routed `FiscalPeriod` read before assuming a regression elsewhere. Levies is triggered from Work Orders and reported/posted from the Reports domain — a genuine Work Orders ↔ Accounting integration point. The Technician Performance Report's payroll-target progress bar (Reports domain) is fed by this module's `CashFlowSummary`, not by Payroll.

### 4.8 Payroll

**Data model.** `PayrollTransaction`: `transaction_type` ∈ Paycheque/Remittance/Adjustment; `amount` and `additional_deductions` are both genuinely `text` (§3 — cast/parse accordingly, do not "fix" to native numeric/jsonb types without explicit direction, since existing call sites depend on the current types).

**Business logic.** Add Paycheque/Remittance support manual entry or a `.txt` "PayPRO" export upload parsed by the pure-parser `autopro-parsePayrollFile` (regex extraction only, no DB access). Manual Paycheque/Remittance creates intentionally omit `created_by`/`created_by_id` (pre-existing behavior, not a bug); Add Adjustment sets them.

**Mark Paid → GL** (`MarkPaidModal.jsx`, the highest-risk piece): a client-side debit/credit balance check runs before any writes. Per selected transaction, in a **deliberately sequential** (not parallelized) loop: marks `is_paid = true`, then inserts a type-specific `BankTransaction`. After the loop, one **bulk** `GLTransaction` insert covers all selected transactions, then `autopro-calculateBankBalances` runs once for the account. GL account mapping: `5008`/`5009` wages, `2054` income tax, `2052` CPP, `2053` EI, `5006`/`5007` employer CPP/EI expense (adjustments instead post to a user-selected account via a GL-account combobox, e.g. `5005`).

**Reversal.** `handleDelete` on an unpaid transaction inserts a reversal-adjustment row (negative amount) rather than deleting — paid transactions aren't deletable through the UI by design.

**Integration.** → **Banking**: `MarkPaidModal.jsx` reads `BankAccount`/writes `BankTransaction`/`GLTransaction` directly — Payroll has no bank/GL tables of its own, and shares write access to the same accounts other modules use (this is normal in this codebase; entity writes are shared freely across modules even though file ownership is siloed). → **Auth/Employee**: reads `pay_rate`/`pto_eligible`/etc. but does not own or write them (owned by Setup's Tech Directory).

### 4.9 Reports

Pure read-only aggregation layer with no dedicated schema — every report is a native `autopro-get*` Edge Function querying other modules' tables directly and returning a computed shape; large scans use a paginated `fetchAllRows` helper (1000-row `.range()` pages) since some source tables exceed default row caps.

**Report inventory:** Customer Report (per-customer sales aggregation), Other Charges Breakdown (non-parts/labor charge aggregation from `line_items` across a date range), **Sales Analysis Report** (fuzzy-matches WO RO numbers to WorkPRO `Project`s, attributes labor cost via `Employee.pay_rate × ProjectTimeSession` time, computes revenue/cost/margin), **Technician Performance Report** (per-tech utilization/efficiency from `TimeRecord`/`ProjectTimeSession`/`UnassignedTime` vs. WO-attributable hours, plus a payroll-target progress bar sourced from Accounting's `CashFlowSummary` — a deliberately separable, lower-fidelity feature from the utilization/efficiency numbers), Work Order Summary (aging buckets, WIP revenue/cost, 30-day closed-revenue comparison, status breakdown — `WorkOrder.status` is already human-readable text, no lookup needed), Inventory On Order, Parts Movement (backed directly by the `get_parts_movement_v2` RPC, not an Edge Function).

**Integration.** Reads across virtually every module (Work Orders, WorkPRO, Employee, Customer, Supplier, InventoryItem) — since it's read-only and every touched table already has permissive RLS, Reports carries none of the write-safety concerns other modules do. Report access gating (e.g. Sales Analysis) must check current `Employee` fields (`admin`/`autopro_access_lvl`) — see §4.10.

### 4.10 WorkPRO (Sister Application)

A **technician-facing sister application**, not an AutoPRO module — see §2's framing. Core tables: `Project` (correlated to a Work Order via plain-text `Project.work_order = WorkOrder.wo_number`, **no FK**), `ProjectTimeSession`, `TimeRecord` (clock in/out, keyed by `employee_name`), `UnassignedTime` (unattributed time, keyed by **`user_name`** — a different field name than `TimeRecord`'s `employee_name` for the same concept, not interchangeable). None of these four tables have working DB defaults for `id`/audit fields — every write must set them explicitly, and none has an `updated_by` column, only `updated_date`.

**Business logic.** Clock-in/out toggles `TimeRecord.status` (`'clocked_in'`/`'clocked_out'`), computing `total_hours` on clock-out; a "global" clock-in also writes a matching `UnassignedTime` row when time isn't attributed to a project. **Project archiving on invoice conversion**: converting a WO to an invoice fire-and-forgets an update of all matching, not-yet-archived `Project` rows to `status: 'archived'` with `date_archived` (Mountain-time local date). The tech directory is simply `Employee` rows filtered by `employee_type = 'tech'` — no separate roster/sync mechanism.

**Gotchas.** `Employee.status` (text, e.g. `'active'`) governs active/inactive here, **not** a boolean `is_active`. `employee_type` (`'tech'`/`'non-tech'`) — never `position` (a free-text job title) — is what determines technician status.

### 4.11 Auth / Employee & Permissions

There is **no separate native `User` table** — `Employee` is the sole authoritative identity/permissions record, linked to Supabase Auth via `Employee.mykadr_user_id` (maps to `auth.users.id`). Key fields: `admin` (bool, admin-only UI), `autopro_access_lvl` (text, e.g. `'lvl3_user'` for full executive Accounting access), `accts_pay_access` (bool, gates a *limited* Accounting menu — Cash Drawer + Cash Flow only — distinct from the full executive menu), `paypro_user` (bool, payroll-nav visibility), `dark_mode` (bool). Avatars are always derived client-side as initials from `full_name` — there's no stored avatar/initials field.

**Legacy → native field-name census (permanent reference, not a one-time migration note):** `role` → `admin`; `access_level` → `autopro_access_lvl`; `Paypro_user` → `paypro_user`; `AcctsPayAccess` → `accts_pay_access`. Any code still checking the left-hand legacy names against a native session/Employee object silently evaluates false/undefined rather than erroring — this specific bug class has recurred across multiple unrelated files.

**A missing `Employee` row for a valid Auth session is an expected state**, not exceptional — every identity-consuming code path must degrade gracefully rather than assume `employee` is always populated. `wo_cards`/`OpenNewWindow` were deprecated outright and deliberately not carried forward to any native column.

**Integration.** Virtually every module reads permission fields off the same resolved `Employee` object rather than maintaining separate logic — Scheduling (`Appointment.employee_id`), Work Orders (assigned-staff fields), WorkPRO (clock-in identity), Reports (access gating) all key off this one table.

## 6) User Preferences & Constraints
*   **Data Integrity First:** Double-entry accounting rules and exact inventory quantities are sacred. Prioritize backend constraints (RPCs, triggers) to guarantee data safety.
*   **Consistency:** Keep UI styling consistent with existing modal and table patterns. Do not introduce major UI changes unless requested. Pair every new `bg-*`/`text-*`/`border-*` class with its `dark:` counterpart per the standard palette (full palette/lesson history: `Archive/master_blueprint.md` §7) — dark mode is a fully-supported theme, not an afterthought to retrofit later. Note the app's light-mode page-canvas background is a deliberate exception to "assume white" — see §3's `--background` CSS-variable note.
*   **Transparency:** Provide verbose `console.log`/`console.error` outputs in complex operations (especially GL and Inventory syncing) to aid frontend debugging.
*   **Deployment workflow (mechanics behind §3's live-verification protocol):** The user pushes commits to `origin/development` via GitHub Desktop independently, outside of any AI agent session. `test.kensauto.ca` serves whatever is currently pushed to `development` — local uncommitted changes are invisible there. Check `git log`/`git status` (and whether the branch is up to date with origin) before diagnosing a live-site failure as a code bug in freshly-written code. **`git push` genuinely does not work from an agent's CLI session in this environment** — Bash hangs on a Windows Credential Manager prompt, PowerShell fails outright with "terminal prompts disabled"; there's no cached push-capable credential available to the CLI. Commit locally and hand off for the user to push — don't retry `git push`, it's an expected, permanent limitation here, not a transient failure. Note also: a stale local check of `origin/development` (`git ls-remote`/`git log origin/...` run once, then trusted) can look like "my commits vanished" when in fact other legitimate work simply landed on top of them afterward — re-`git fetch` and check `git merge-base --is-ancestor <mine> <suspect-tip>` before concluding anything was lost or reverted.
*   **Edge function deploys are a separate manual step from the frontend push (see §3)** — after editing anything in `supabase/functions/*`, deploy it explicitly (Supabase MCP `deploy_edge_function`) before asking the user to re-test; don't assume the `origin/development` push workflow covers it.
*   **Direct writes to the production Supabase project (`hbcrwkmgsazqrvsrmxyr`) via MCP tools (`apply_migration`, `execute_sql` DDL, etc.) are gated by Claude Code's own auto-mode classifier**, independent of any in-chat approval — confirmed 2026-08-12 applying the `WorkOrder_Broadcast` fix. The call is blocked outright on first attempt even after explicit user approval in chat, and needs the user to re-confirm through the tool's own permission prompt before it will run. Expect this on any prod-DB write, not just this one instance — it's a standing platform behavior, not a one-off fluke.
