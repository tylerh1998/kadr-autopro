## 1) Context & Lessons Learned

**Core goal:** Port `sendAppointmentReminders` (email) and `sendTextReminders` (SMS) off Base44 onto native `autopro-*` Supabase Edge Functions, scheduled to run automatically every weekday via `pg_cron` — **dev branch only for now.** Production gets its own follow-up plan once this is proven live on dev. **Expanded scope (2026-08-10):** build the two new functions on top of a small shared email/SMS sending module, rather than adding an 8th and 3rd copy-pasted implementation of logic that's already duplicated across the codebase — see the infrastructure review below.

**Why these two are architecturally different from every other base44 call site in this codebase:** every other remaining `base44.*` call is a *frontend* call (`base44.functions.invoke(...)`) routed through `base44-proxy`/`VITE_BASE44_PROXY_URL`, which is hardcoded to production regardless of which Supabase branch the frontend points at. These two have **no frontend caller at all** — they run directly on Base44's own function-hosting platform on some trigger/schedule, and connect to Postgres via raw REST calls using `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` **secrets configured on the Base44 platform itself** (confirmed by reading both `entry.ts` files in full), completely separate from Vercel's env vars. Those secrets point at production. There is no `VITE_*` variable to flip — the only real fix is what this plan does: build native replacements and stop relying on Base44's hosting/scheduling entirely.

**Research performed for this plan (2026-08-10), read in full, not just grepped:**
- `base44/functions/sendAppointmentReminders/entry.ts` (271 lines) and `base44/functions/sendTextReminders/entry.ts` (187 lines) — both read completely. Logic: `fetchAll('Appointment')` (unscoped, table-wide), compute a fixed `-7h` MST offset (**no DST adjustment — a deliberate existing simplification, not a bug to fix here**), for each appointment check `reminders_email`/`reminders_text` + `reminder_days_before` math against "today," build recipient (`reminder_email_address || customer?.email` for email; `reminders_phone` for SMS), log a `pending` `SentEmailLog` row, send via Resend (email, batch API) or Twilio (SMS, one at a time), update the log to `sent`/`failed`.
- **No idempotency guard exists in either original function.** Neither checks whether a reminder was already sent today for a given appointment before sending again. Running the function twice in one day — e.g. a manual test invocation on the same day the scheduled cron fires — would send a duplicate email/SMS to whoever it resolves. This was never a problem for Base44 because there was no scheduler visibility into how often it actually ran; it becomes a real, first-class design concern the moment we own the scheduler ourselves. **This plan adds a guard; see Phase 3/4.**
- **Live schema confirmed (dev branch, `information_schema.columns`):** `Appointment` has `reminders_email`(bool)/`reminders_text`(bool)/`reminder_email_address`(text)/`reminders_phone`(text)/`reminder_days_before`(int)/`start_time`(genuine `timestamptz`, not the text-date gotcha some other tables have)/`customer_id`/`vehicle_id`/`notes`/`id`(text, no DB default — must be client-generated, 24-char-hex per project convention). `SentEmailLog` confirmed to have every column both original functions (and the native reference functions) already write to.
- **`pg_cron` is available on the dev project but not yet installed** (`list_extensions`: `pg_cron` present, `installed_version: null`). **`pg_net` is already installed** (`0.20.4`) — this is what a cron job will use to actually call an Edge Function over HTTP. **`supabase_vault` is also already installed** (`0.3.1`). No `pg_cron`/`net.http_post` usage exists anywhere in this repo's tracked migrations today — this is a first-of-its-kind infra pattern for this project, worth documenting clearly for whoever touches cron next.
- **Deliberately avoiding a repeat of an already-documented security anti-pattern:** `master_blueprint.md` flags two production triggers (`sync_customer_to_google`, `WorkOrder_Broadcast`) that call external webhooks with a **live JWT hardcoded in plaintext directly in the trigger definition**, readable by anyone with schema access. A `pg_cron` job's SQL body is visible the same way via the `cron.job` table. This plan stores the shared secret the cron job needs in `supabase_vault` instead of inlining it in migration SQL — see Phase 1.

**Lessons learned, carried forward from the broader migration effort (still true here):**
- A committed source fix and a *deployed* function are two separate steps — never assume a git push updates a live Edge Function; always explicitly deploy and confirm via `get_edge_function`'s `updated_at`/version.
- Supabase secrets are write-only — once set, nothing (CLI, dashboard, or this session's tools) can read the value back, only overwrite it or check presence indirectly.
- New Edge Functions in this project are always named `autopro-[functionname]`.
- `Promise.all`-poisoning and stale documentation are both real, recurring risks in this codebase — this plan's own verification steps double-check against live source rather than trusting any prior note, including this plan's own assumptions once they're written.
- **(New)** Don't let a legitimately-useful cleanup (the shared `_shared/` module) expand silently into touching already-in-production, revenue/customer-facing functions without an explicit separate go-ahead — Phase 2 below is scoped to be purely additive (new files, zero call sites changed) for exactly this reason; retrofitting the 6 existing functions to actually use it is its own explicitly-deferred phase (Phase 6), not bundled in.
