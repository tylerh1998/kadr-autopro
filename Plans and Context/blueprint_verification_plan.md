**Operational notes for whoever continues live testing (carried forward + new from 2026-08-09):**
- Login is manual — the user signs into `test.kensauto.ca` themselves with their own `test@kensauto.ca` credentials. If you hit an auth wall, stop and ask; don't guess credentials. (This session, the browser session was already authenticated/persisted from before — didn't need a fresh login.)
- `window.confirm()`/`window.alert()` dialogs auto-resolve to "cancel"/get suppressed in this Browser-pane environment unless overridden — run `window.confirm = () => true; window.alert = (msg) => console.log('ALERT:', msg);` via `javascript_tool` at the start of any session on a new page before any confirm/alert-gated submit.
- **The Browser pane's `computer` tool (coordinate-based click/screenshot) does not reliably work when the pane isn't visually displayed on the user's screen** — screenshots time out, and coordinate clicks frequently land on the wrong element or no-op. **Prefer `javascript_tool`-dispatched clicks on elements found via DOM query** (`document.querySelectorAll` + `.click()`) for all interaction this session; use `read_page`/`find` refs with the `computer` tool only when `javascript_tool` genuinely can't resolve the target. `form_input` (the dedicated tool) is the reliable way to set text/number input values into React-controlled fields — a raw `javascript_tool` native-setter-plus-`input`-event approach worked for combobox search fields but was NOT reliable for some number inputs (reproduced on `LineOfCreditTransactionModal.jsx`'s Charge Amount field, where it silently failed to update React state even though the DOM `.value` looked correct) — prefer `form_input` for any field where correctness matters, fall back to the native-setter trick only for combobox/popover search boxes.
- **Right-click `ContextMenu` is a recurring interaction pattern for row-level actions app-wide**, not just Suppliers/Inventory — confirmed this session on `ChartOfAccounts.jsx`, `LineItemsTable.jsx` (WO parts grid), and `InventoryReturns.jsx`. Rows styled `cursor-pointer` with no obvious left-click handler are a strong signal to try `dispatchEvent(new MouseEvent('contextmenu', ...))` before concluding a row action is broken or unreachable.
- Some dialog-open buttons open a **second, nested dialog** on top of the first without closing it (e.g. `LineOfCreditPaymentModal`'s "Add Manual Transaction" over the account-edit form when both were left open) — if `document.querySelectorAll('[role="dialog"]').length > 1`, always target the *last* one, and don't assume clicking a field only affects the dialog you think is active.
- Popover-style comboboxes (GL account pickers in Journal Entries, LOC transaction/payment modals, SupplierTx) share one pattern: click the combobox trigger, then set the internal search `<input>` via the native-value-setter + `input`-event trick, then click `wrapper.querySelector('.max-h-\\[260px\\]').children[0]` (or the matching item) — this worked consistently everywhere it was tried this session.
- The top nav's dropdowns (Reports, Accounting sub-items, etc.) are **hover**-triggered (`onMouseEnter` React state), not click — dispatch a synthetic `mouseover` on the nav item's container, wait briefly, then interact with the revealed items; some are **nested two levels deep** (e.g. `Inventory` → `Reports` → individual report cards inside a modal) — the inner "Reports" hover target needs an actual `.click()` (not just hover) to open the modal. Full technique and confirmed entry points are in Section 4.

Override `window.open` (`window.open = (...args) => { console.log(args); }`) to log the intended URL first if unsure what it would have opened.

Any staff member typing a customer's full first+last name gets zero results and has to know to fall back to last-name-only. **Fix:** add `lower(btrim(coalesce(first_name,'') || ' ' || coalesce(last_name,''))) like '%' || lower(p_search_term) || '%'` (and ideally the exact-match variant) to the `WHERE` clause, mirroring what the `ORDER BY` already assumes exists. Note: this is a pre-existing bug in a Phase 5–era RPC, unrelated to anything Phase 13 or later touched — the Appointment customer-search dialog (`AppointmentForm.jsx`) uses a *different* search mechanism and was directly confirmed working correctly with the exact same "Tyler Haney" full-name query earlier in this session, which is what surfaced the discrepancy.
